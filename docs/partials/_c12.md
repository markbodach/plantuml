## Chapter 12: Debugging and Diagnostics

### Overview

The framework provides reusable debugging and diagnostic utilities that assist with:

- Variable inspection
- Theme troubleshooting
- Style troubleshooting
- Color resolution analysis
- Runtime validation
- Framework development

Unlike troubleshooting guidance, debugging utilities help visualize and inspect the framework's internal state while diagrams are being generated.

Most diagnostic helpers generate formatted text that can be rendered inside:

```text
Rectangle
Note
Legend
Title
```

This makes it possible to inspect framework state without relying exclusively on `!log` statements.

---

### Debugging Philosophy

When a diagram does not render as expected, validate assumptions before modifying framework code.

Variables and colors often resolve through multiple abstraction layers:

```text
Theme Variable
    ↓
Semantic Token
    ↓
Color Resolver
    ↓
Generated Style
    ↓
Diagram Element
```

Diagnostics help confirm which layer is producing an unexpected result.

---

### Variable Diagnostics

#### Single Variable

Inspect a single variable value.

```plantuml
rectangle $debug_variable(
    "COLOR_PRIMARY",
    $COLOR_PRIMARY
)
```

Result:

```text
COLOR_PRIMARY = #D6EAF8
```

This helper is useful when validating individual values and override behavior.

---

### Variable Collection Diagnostics

The framework supports two approaches.

#### Flat Variable Collection

Recommended for maximum PlantUML compatibility.

```plantuml
rectangle $debug_panel(
    "Theme Variables",
    $debug_variables_flat([
        "COLOR_PRIMARY",$COLOR_PRIMARY,
        "COLOR_TEXT",$COLOR_TEXT,
        "ROUND_2",$ROUND_2
    ])
)
```

Result:

```text
COLOR_PRIMARY = #D6EAF8
COLOR_TEXT    = #000000
ROUND_2       = 10
```

#### Nested Variable Collection

Supported when nested arrays are available.

```plantuml
rectangle $debug_panel(
    "Theme Variables",
    $debug_variables_nested([
        ["COLOR_PRIMARY",$COLOR_PRIMARY],
        ["COLOR_TEXT",$COLOR_TEXT],
        ["ROUND_2",$ROUND_2]
    ])
)
```

Nested collections are easier to read but may be less portable across PlantUML versions.

Preference should be given to flat collections unless nested arrays have been validated in the target runtime.

---

### Color Diagnostics

Color diagnostics are designed to assist with semantic color resolution and style generation.

Example:

```plantuml
rectangle $debug_color(
    "Web UI",
    $cBackgroundColor,
    $cFontColor,
    $cLineColor
)
```

Output:

```text
Web UI

Background = #D6EAF8
Font       = #000000
Line       = #345678
```

Use this helper when troubleshooting:

- AUTO text colors
- Semantic color resolution
- Theme overrides
- Line color generation
- Style inheritance

---

### Style Diagnostics

Style diagnostics expose a complete style context.

Example:

```plantuml
rectangle $debug_style(
    "Component",
    $backgroundColor,
    $fontColor,
    $lineColor
)
```

Typical output:

```text
Component

Background = #D6EAF8
Font       = #000000
Line       = #345678
```

Useful when validating:

```text
AUTO
CURRENT
DARKEN
LIGHTEN
```

processing.

---

### Debug Panels

Debug panels provide a consistent visual structure for diagnostics.

Example:

```plantuml
rectangle $debug_panel(
    "Resolved Style",
    $debug_variables_flat([
        "Background",$backgroundColor,
        "Font",$fontColor,
        "Line",$lineColor
    ])
)
```

Output combines a title and diagnostic content into a single formatted block.

Debug panels are particularly useful during framework development and theme authoring.

---

### Theme Diagnostics

Theme diagnostics help validate registration and execution behavior.

#### Registration Validation

```plantuml
!log $Is_Theme_Registered("Corporate")
```

#### Theme Execution Tracing

Example diagnostic logging:

```plantuml
!log "Invoking Theme=[" + $theme + "]"
```

This can be temporarily inserted into:

```plantuml
Invoke_Preload_Themes()
Invoke_Load_Themes()
```

to validate execution order.

---

### Runtime Inspection Workflow

When validating unexpected behavior:

```text
Theme Registration
    ↓
Variable Values
    ↓
Semantic Colors
    ↓
Resolved Colors
    ↓
Generated Styles
    ↓
Rendered Diagram
```

Use diagnostics to identify the first point where actual behavior differs from expected behavior.

---

### Recommended Debugging Patterns

#### Inspect Resolved Colors

```plantuml
rectangle $debug_color(
    "Panel Style",
    $backgroundColor,
    $fontColor,
    $lineColor
)
```

#### Inspect Theme Variables

```plantuml
rectangle $debug_panel(
    "Theme",
    $debug_variables_flat([
        "COLOR_PRIMARY",$COLOR_PRIMARY,
        "COLOR_TEXT",$COLOR_TEXT
    ])
)
```

#### Inspect Individual Values

```plantuml
rectangle $debug_variable(
    "ROUND_2",
    $ROUND_2
)
```

---

### Best Practices

- Remove diagnostics from production diagrams unless intentionally documenting framework behavior.
- Prefer diagnostic panels over large volumes of log statements.
- Use flat-variable collections when maximum compatibility is required.
- Validate assumptions before modifying framework logic.
- Use color diagnostics when troubleshooting semantic color resolution.
- Confirm variable values before investigating style-generation logic.
- Use diagnostics as temporary inspection tools rather than permanent diagram content.

---

### Design Summary

The debugging utilities provide a lightweight diagnostic framework for inspecting variables, colors, styles, and theme behavior.

For day-to-day troubleshooting, most consumers will primarily use:

```plantuml
$debug_variable()
$debug_panel()
$debug_color()
```

while more advanced helpers remain available for framework development and runtime investigation.

Together, the troubleshooting guidance in Chapter 11 and the diagnostic capabilities described in this chapter provide a complete workflow for identifying, understanding, and resolving framework issues.
